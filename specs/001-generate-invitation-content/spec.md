## User Scenarios & Testing *(mandatory)*

### User Story 1 - 확정 정보를 입력해 청첩장 생성 (Priority: P1)

청첩장 작성자는 정해진 입력 파일에 이름, 예식 일시와 장소, 길찾기 링크, 사진을 등록하고 스크립트를 실행해 청첩장을 생성한다. 수정할 일이 생기면 같은 파일의 값을 바꾸고 다시 실행한다.

**우선순위 근거** — 반복되는 정보 입력과 수정에 AI를 사용할 필요가 없어진다.

**독립 검증** — 안내만 보고 입력 파일의 날짜를 다른 달로, 장소를 다른 예식장으로 바꾼 뒤 청첩장을 생성한다. 페이지 제목, 표지, 인사말, 일정, 달력과 길찾기에서 각 항목이 최신 입력값에 맞는지 확인한다.

1. **Given** 이름, 예식 일시와 장소, 길찾기 링크, 사진이 입력되어 있을 때 **When** 작성자가 안내된 명령을 실행하면 **Then** AI나 페이지 직접 수정 없이 이 정보가 반영된 정적 청첩장이 생성된다.
2. **Given** 청첩장이 한 번 생성되었을 때 **When** 예식 날짜를 다른 달로 변경해 다시 생성하면 **Then** 표지와 일정에 새 날짜와 요일이 표시되고 달력도 새 월과 예식일을 표시한다.

---

### User Story 2 - 잘못된 입력을 찾아 수정 (Priority: P2)

작성자는 필수 항목을 빠뜨리거나 형식이 잘못된 값을 입력했을 때 어떤 값을 고쳐야 하는지 확인한다.

**우선순위 근거** — 입력 실수 때문에 미리보기나 게시에 쓰던 청첩장이 불완전한 결과로 바뀌는 일을 막는다.

**독립 검증** — 한 번 생성한 페이지를 기준으로 필수 값 누락, 존재하지 않는 날짜, 잘못된 시각, 형식이 잘못된 길찾기 주소, 존재하지 않는 사진을 각각 입력해 실행한다.

1. **Given** 필수 값이 누락되었거나 올바르지 않을 때 **When** 작성자가 생성 명령을 실행하면 **Then** 실행이 실패하고 문제가 있는 항목과 이유를 알려주며 마지막으로 성공한 페이지를 보존한다.
2. **Given** 이전 생성이 입력 오류로 실패했을 때 **When** 작성자가 입력을 고쳐 다시 실행하면 **Then** 수정된 값으로 청첩장이 생성된다.

---

### User Story 3 - 초안을 미리보고 확정 정보만 게시 (Priority: P3)

작성자는 정보가 확정되기 전에는 예시로 미리보고, 게시할 때는 확정 정보와 사진이 들어간 결과를 확인한다.

**우선순위 근거** — 초안을 검토하는 동안 예시 정보나 공개를 결정하지 않은 개인정보가 하객에게 제공되는 것을 막는다.

**독립 검증** — 예시 입력으로 미리보기를 생성한 뒤 게시를 시도한다. 이어서 확정 입력으로 생성한 결과를 기존 게시 경로에서 확인한다.

1. **Given** 개발용 예시 정보가 사용되었을 때 **When** 작성자가 생성 결과를 미리보고 게시를 시도하면 **Then** 미리보기에서 초안임을 식별할 수 있고 게시가 차단된다.
2. **Given** 작성자가 필수 정보와 사진을 확정했을 때 **When** 게시용 결과를 생성하고 검토하여 게시하면 **Then** 하객은 모바일과 데스크톱에서 확정 정보를 읽고 같은 예식장을 가리키는 길찾기 링크를 사용할 수 있다.

### Edge Cases

- 홀 이름이나 층을 입력하지 않으면 해당 항목을 생략한다.
- 첫 생성이 실패하면 불완전한 페이지를 생성 결과로 남기지 않는다.
- 입력에 한글, 인용부호 또는 앰퍼샌드가 포함되면 청첩장에 의도한 글자가 표시된다.
- 이전에 게시용 페이지를 생성했더라도 현재 입력이 예시이거나 유효하지 않으면 이전 결과를 현재 입력의 게시용 결과로 사용할 수 없다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001** — 작성자는 한 입력 파일에서 신랑·신부 이름, 예식 날짜와 시작 시각, 예식장 이름과 주소, 길찾기 링크, 표지 사진을 관리할 수 있어야 한다. 홀 이름과 층은 선택 항목으로 두고 입력한 경우 표시해야 한다.
- **FR-002** — 작성자는 저장소에서 안내된 명령 한 번으로 입력 파일의 정보가 반영된 청첩장을 다시 생성할 수 있어야 한다. 이 작업에는 AI 호출, AI 계정 또는 페이지 직접 편집이 필요 없어야 한다. 안내에는 항목별 입력 예시와 로컬 미리보기 절차가 있어야 한다.
- **FR-003** — 이름은 페이지 제목, 표지, 인사말 등 표시되는 모든 위치에서 동일한 입력값을 사용해야 한다. 예식 날짜와 시작 시각은 표시되는 모든 위치에서 동일한 입력값과 일치해야 하며, 표시되는 요일, 달력 월, 강조된 예식일 및 오전·오후 표기는 입력값과 일치해야 한다. 예식장과 주소, 길찾기 링크, 표지 사진은 작성자가 입력한 값을 반영해야 한다.
- **FR-004** — 생성 과정은 필수 값의 누락, 유효하지 않은 날짜나 시각, 형식이 잘못된 길찾기 링크, 존재하지 않는 사진을 발견하면 항목과 이유를 알려주고 실패해야 한다. 결과를 새로 남기거나 이전에 성공한 페이지를 덮어쓰기 전에 입력을 검증해야 한다.
- **FR-005** — 예시 정보로 생성된 페이지에는 초안 표시가 있어야 한다. 게시 과정은 현재 입력이 유효하고 작성자가 확정한 정보와 사진으로 생성된 결과만 허용해야 하며, 예시 데이터와 사진은 공개 배포본에서 제외해야 한다.
- **FR-006** — 생성 페이지는 기존 GitHub Pages 프로젝트 경로 `/wedding/`에서 리소스를 불러올 수 있어야 한다. 모바일과 데스크톱에서 예식 일시와 장소를 가로 스크롤 없이 읽을 수 있어야 하며, 길찾기 링크는 모바일 터치와 데스크톱 마우스·키보드로 이용할 수 있어야 한다.

### Key Entities *(include if feature involves data)*

- **청첩장 입력 정보** — 작성자가 입력한 신랑·신부 이름, 예식 일시, 예식장 정보, 길찾기 링크와 표지 사진. 예시와 확정 정보를 구분한다.
- **생성된 청첩장** — 입력값을 제목과 본문, 일정과 달력, 사진과 길찾기에 반영한 정적 페이지. 로컬에서 검토할 수 있으며 확정 결과는 게시에 사용한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001** — 작성자는 예식 날짜와 장소를 바꾸고, 문서에 나온 생성 명령을 한 번 실행해 AI 사용과 페이지 직접 편집을 각각 0회로 유지하며 변경 결과를 확인할 수 있다.
- **SC-002** — 날짜를 다른 달로 옮긴 검증에서 이름, 날짜, 요일, 일시, 달력 월과 강조일, 장소와 링크를 표시하는 모든 위치가 최신 입력과 일치한다.
- **SC-003** — 필수 값 누락, 잘못된 날짜, 잘못된 시각, 잘못된 링크 형식, 누락된 사진의 5개 검증 사례 모두에서 문제 항목을 식별할 수 있고 기존 성공 결과가 보존된다.
- **SC-004** — 예시 입력으로 시도한 게시 1건은 차단되고, 확정 입력으로 생성한 게시본에는 예시 정보와 사진이 0건 포함된다. 게시본은 모바일과 데스크톱에서 일시와 장소 표시, 리소스 로드, 길찾기 링크 검증을 모두 통과한다.

## Assumptions

- 정보 입력의 기본 흐름은 저장소에서 입력 파일을 편집하고 작성자가 직접 생성 명령을 실행하는 방식이다. 기존 표지 사진과 예식 안내의 갱신을 범위로 잡고, 브라우저 편집 화면, 게시 자동 시작, 가족 소개와 연락처·계좌번호 추가는 범위 밖으로 둔다.
- 작성자가 확정 정보와 사진을 제공한다. 게시 전 작성자는 로컬 미리보기에서 표시값을 확정 정보와 대조하고 링크가 같은 예식장으로 연결되는지 확인한다. 게시 후에는 모바일과 데스크톱에서 게시된 내용과 링크를 다시 확인한다.
